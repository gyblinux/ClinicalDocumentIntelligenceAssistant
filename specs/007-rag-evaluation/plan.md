## Summary

Add an offline evaluation stage that measures feature 006 pipeline quality with a
fixed 20-40 case set and writes reproducible per-case, aggregate, and comparison
reports. Add a deterministic plain-text presentation layer over saved pipeline and
answer artifacts.

Presentation uses validated claims and citations, not raw model output. It shows a
concise answer paragraph, all claim/source details, status, limitations, and an
optional exact-match evaluation verdict. It never presents a per-answer trust
percentage.

## Technical Context

**Language/Version**: Python 3.11+

**Primary Dependencies**: Existing standard library, `pytest`, and current project
artifacts; no new framework or evaluator service

**Evaluation Input**: Versioned local JSON case set with 20-40 cases

**Pipeline Input**: Saved feature 006 pipeline records, or pipeline records
generated by invoking the existing orchestration service

**Storage**: Local JSON evaluation artifacts and plain-text presentation artifacts

**Testing**: `pytest` with fixed fixtures and deterministic rubric cases; optional
Docker integration for pipeline generation

**Target Platform**: Host Python CLI on Windows

**Project Type**: Single Python package with `clinical-doc-eval` and
`clinical-doc-present` commands

**Performance Goals**: Evaluate the fixed 20-40 case set in one run; presentation
must produce fewer than 1,000 words and a summary paragraph of at most 180 words

**Constraints**: Evaluation and presentation are read-only, no answer withdrawal,
no automatic prompt rewriting, no per-answer trust percentage, and no LLM judge in
the first baseline

**Scale/Scope**: One corpus, one collection, 20-40 fixed cases, one presentation at
a time, and one declared change per comparison

## Design

### Evaluation Case Set

Use one versioned JSON document containing 20-40 cases:

- Unique `case_id`
- `question`
- `answerability`: `answerable` or `unanswerable`
- Expected evidence IDs
- Required key points
- Forbidden or contradicted statements
- Rubric version and case-level scoring fields

Invalid case count, duplicate IDs, missing fields, unknown answerability, or
malformed expected evidence fails before running pipelines.

### Baseline Execution

The evaluation runner supports two inputs:

1. One saved feature 006 pipeline record per case.
2. A request to execute feature 006 for every case.

For execution, feature 007 reuses the existing orchestration service through an
injectable protocol. It must not invoke CLI subprocesses. Saved mode makes tests
and reruns independent of Docker.

Each case result records:

- Input case and test-set version
- Pipeline, retrieval, and answer artifact IDs/paths
- Question and configuration fingerprint
- Retrieval metrics
- Citation validity
- Faithfulness/rubric result
- Refusal correctness
- Presentation checks when rendered
- Latency and available token/cost usage
- Failure codes and intervention category

### Deterministic Metrics

Initial metrics:

- `retrieval_hit_at_k`: at least one expected evidence ID retrieved
- `retrieval_recall_at_k`: retrieved expected evidence / all expected evidence
- `retrieval_mrr`: reciprocal rank of the first expected evidence item
- Citation validity: every answer citation resolves to supplied evidence
- Citation coverage: every factual claim has at least one citation
- Required key-point coverage: normalized occurrence of fixed required phrases
- Forbidden-statement violations: normalized occurrence of explicitly disallowed
  claims
- Refusal correctness: expected answerability matches answer/abstention status
- Latency and usage: copied from pipeline and answer records

The first key-point matcher is deterministic and intentionally limited. It is a
reproducible proxy, not semantic proof. A human-reviewed sample remains part of
acceptance, and an LLM judge may be added only later.

### Failure Diagnosis

Versioned failure codes include:

- `retrieval_miss`
- `retrieval_low_rank`
- `missing_citation`
- `invalid_citation`
- `missing_required_fact`
- `forbidden_claim`
- `false_answer`
- `over_refusal`
- `stage_failure`
- `presentation_integrity_error`
- `presentation_too_long`

Each failed case maps to one intervention category:

- retrieval configuration
- chunking/indexing
- answer prompt
- citation generation
- abstention policy
- presentation renderer
- evaluation case/rubric
- no change recommended

### Baseline and Comparison

An evaluation run persists aggregate metrics and a configuration fingerprint.
Comparison requires:

- Same test-set and rubric versions
- Same case IDs
- Exactly one changed configuration variable
- Baseline and candidate reports with their artifact links

The report shows metric deltas, latency/cost deltas, and the declared changed
variable.

### Plain-Text Presentation

Default format is plain text with these sections:

```text
ANSWER
QUALITY
SUPPORTING DETAIL
SOURCES
LIMITATIONS
```

Rules:

- Build the summary paragraph only from existing validated claims in their original
  order.
- Target 3-5 claims and at most 180 words.
- Include every claim in `SUPPORTING DETAIL`.
- Assign source numbers by first citation appearance.
- Deduplicate sources by canonical `source_url + nct_id`; aggregate sections.
- Keep the complete rendered view below 1,000 words.
- If complete non-truncated rendering exceeds the limit, fail with
  `presentation_too_long`.
- Never use raw `model_output` as displayed answer content.
- Never omit a validated claim or citation.

### Evaluation Verdict in Presentation

Per-answer verdicts display only when all keys match:

```text
answer_id
pipeline_id
case_id
suite_version
rubric_version
configuration_fingerprint
```

The view shows versioned pass/fail checks. It shows "not independently evaluated"
when no matching verdict exists. It never displays a trust percentage.

### Commands

```text
clinical-doc-eval run \
  --cases PATH \
  [--pipeline-map PATH] \
  [--collection NAME] \
  [--limit 5] \
  [--output-dir artifacts/evaluations]

clinical-doc-eval compare \
  --baseline PATH \
  --candidate PATH \
  [--output PATH]

clinical-doc-eval review \
  --input PATH \
  [--output-dir artifacts/evaluations/presentation-reviews]

clinical-doc-present \
  --pipeline PATH \
  [--case-id CASE_ID] \
  [--evaluation PATH] \
  [--output PATH]
```

`--case-id` is required to display a case-specific verdict. Without it, the view
must report that semantic quality was not independently evaluated for the exact
answer.

When `--pipeline-map` is omitted, evaluation generates pipelines through feature
006 using collection `clinical_evidence_v1` and retrieval limit `5` by default.
When a map is supplied, it must contain exactly one entry for every case ID, with no
missing or unknown IDs.

Standard output is one JSON report/result object. Presentation writes plain text
and prints the same text. Human diagnostics go to standard error.

### Human Readability Check

Use a 0-2 rubric:

- Direct answer
- Claim completeness
- Citation clarity
- Structure
- Caution/limitations

Target at least 8/10 with no zero for citation clarity or caution. Review five
representative rendered cases: two answerable, one multi-source, one conflicting,
and one unanswerable.

Persist each review under:

```text
artifacts/evaluations/presentation-reviews/<review_id>.json
```

The record includes reviewer, date, rubric version, five case IDs, criterion
scores, aggregate score, threshold result, and notes.

The `review` command validates and persists this input without attempting to infer
human scores.

## Testing Strategy

- Case-set boundary, schema, duplicate, and rubric validation.
- Retrieval hit/recall/MRR calculations.
- Citation validity, coverage, required/forbidden phrase detection.
- Refusal correctness and stage failure attribution.
- Baseline and one-variable comparison.
- Presentation determinism, summary limit, total word limit, all-claim coverage,
  source deduplication, and citation integrity.
- Unevaluated, matching verdict, mismatched verdict, abstention, and failure views.
- No raw model output in user-facing answer content.
- CLI JSON/text and exit codes.
- Optional Docker integration for generated pipeline records.

## Complexity Tracking

No violations. Presentation is deterministic and local; the baseline evaluator uses
transparent text/ID checks. No vector metrics service, hosted evaluator, dashboard,
or second LLM is introduced.
